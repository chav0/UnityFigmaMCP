# Build Prefab — Figma to Unity

This skill walks through building a Unity UI prefab from a Figma node. It's an interactive
workflow: you show the user what they're about to build, let them choose how, run the build,
and report what happened — including what sprites are missing so they can deal with those
separately.

## Input

The user needs to provide:
- **Figma file key** — the key from the Figma URL (`figma.com/file/<key>/...`)
- **Node ID** — the specific frame or component to build (`123:456`)
- **Prefab name** — what to call the resulting prefab

Optional:
- **Save path** — where to save (defaults to the project's prefab folder from settings)
- **Pipeline ID** — which pipeline to use (defaults to first available)

If the user gives a Figma URL, extract the file key and node ID from it.

## Workflow

### Step 1 — Fetch the Figma node

Call `figma_get_node` with the file key and node ID. This downloads the full node tree
and saves it locally for the build pipeline to use.

### Step 2 — Show preview

Do these two calls in parallel:
- `figma_export_image` — export the node as a PNG at 1x scale (pass `[nodeId]`), then show the image to the user
- `figma_get_node_names` — get the slim hierarchy tree

Display the hierarchy to the user, but limit to 3 levels deep to keep it readable.
The user needs to see what they're about to build — the structure might be more complex
than expected, or it might be the wrong node.

### Step 3 — Rename objects in Figma

If the root node is NOT a component (i.e. it's a plain FRAME), review the hierarchy
from Step 2 and identify nodes with generic auto-generated Figma names like "Frame 32",
"Group 5", "Rectangle 1", "Vector", etc. Rename them directly in the Figma file
using the Figma MCP before building — the prefab will inherit the correct names.

Use PascalCase and name objects by their purpose:

| Role | Prefix | Examples |
|------|--------|----------|
| Layout / background container | `Layout` | `LayoutHeader`, `LayoutContent`, `LayoutRow` |
| Icon / image | `Icon` | `IconLock`, `IconStar`, `IconCoin` |
| Button | `Button` | `ButtonPlay`, `ButtonClose`, `ButtonSettings` |
| Title text | `Header` | `HeaderScreen`, `HeaderSection` |
| Subtitle / body text | `Description` | `DescriptionHint`, `DescriptionPrice` |
| Small label / caption | `Label` | `LabelCount`, `LabelStatus`, `LabelTimer` |
| Separator line | `Separator` | `Separator`, `SeparatorHorizontal` |
| Scrollable area | `Scroll` | `ScrollContent`, `ScrollList` |
| Toggle / checkbox | `Toggle` | `ToggleSound`, `ToggleNotifications` |
| Progress bar / slider | `Progress` | `ProgressHP`, `ProgressXP` |
| Avatar / portrait | `Avatar` | `AvatarPlayer`, `AvatarOpponent` |

Infer the role from the node's children, size, components, and context in the hierarchy.
A frame wrapping other frames is a Layout. A small image is an Icon. A frame with a text
child and a background is likely a Button.

Skip renaming if:
- The node is a COMPONENT or COMPONENT_SET (names come from the designer)
- The name already looks intentional (not auto-generated by Figma)

After renaming, re-fetch the node (`figma_get_node`) so the build uses the updated names.
If no renames were needed, skip the re-fetch and proceed.

### Step 4 — Choose pipeline

Call `unity_get_pipelines` to get available pipelines.

If there's only one pipeline, mention it and proceed. If there are multiple, list them
with their IDs and steps, and ask the user to pick one. If the user already specified
a pipeline ID, use that.

### Step 5 — Build

Call `unity_build_prefab` with:
- `fileKey`
- `nodeId`
- `prefabName`
- `savePath` (if specified)
- `pipelineId` (chosen or default)

This is the heavy operation — it sends the Figma tree to Unity, runs all pipeline steps
(Text, RectTransform, Image, Layout, ContentSizeFitter, etc.), and saves the result
as a `.prefab` asset.

### Step 6 — Inspect result

Call `unity_get_hierarchy` on the newly created prefab to get the actual Unity hierarchy
with all components and properties.

### Step 7 — Verify variants (COMPONENT_SET only)

When the built node is a COMPONENT_SET, the response includes a `variants` array alongside
the base prefab. Variant properties (text, colors, visibility, sizes, layout) are applied
automatically during build — each variant prefab already reflects its Figma variant data.

Check whether any variant uses sprites that differ from the base. If so, export them
via `unity_save_sprites` (batch). If a variant needs further tweaks beyond what the
pipeline handled, use `unity_edit_prefab`.

### Step 8 — Report

Present a build report in the user's language:

```
## Build Report

Prefab: Assets/UI/Prefabs/MyScreen.prefab
Pipeline: default (7 steps)
Source: figma.com/file/<key>, node 123:456

### Hierarchy
<show the Unity hierarchy from step 6, formatted as a tree>

### Variants (if COMPONENT_SET)
- Button_Hover — Assets/UI/Prefabs/Button_Hover.prefab (edited: color, text)
- Button_Pressed — Assets/UI/Prefabs/Button_Pressed.prefab (edited: color, scale)

### Missing Sprites
The following sprites were referenced but not found in the project:
- icon-search (node 125:789)
- bg-card (node 126:100)

Use `/download-sprites` to import them, then rebuild or update the prefab.
```

If there are no missing sprites, say so — that's a good outcome worth noting.

## Important notes

- This skill does NOT download sprites. If the build references sprites that aren't
  in the project, they'll be missing in the result. The user should run `/download-sprites`
  before or after building. The report lists what's missing so they know exactly what to get.

- Binding (`/bind-figma-unity`) is **not required** before building. The pipeline
  registers component and sprite keys automatically during build. Binding is only
  useful for old UI kits where assets already exist but lack Figma keys.

- After building, the user may want to refine the result — restructure hierarchy,
  adjust layout, remove wrappers. That's a separate task, not part of this skill.
